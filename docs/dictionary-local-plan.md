# 离线词典 · 纯本地落地记录

> 定位：把「查词」从一次联网请求，变成一件**本地文件处理**。
> 数据源：CC-CEDICT（<https://cc-cedict.org>，CC BY-SA 4.0）。
> 不引入任何 npm 依赖，不新增 WASM，不发起任何跨域请求。

---

## 1. 结论先行

**已集成，路由 `/dictionary`，归入「文字 / 查阅」分组，首页第 48 张卡片。**

- 内核 `src/lib/dict.js`：解析 / 索引 / 检索三层，**纯函数、零 DOM**，`node --test` 可单测。
- 视图 `src/views/Dictionary.vue`：搜索、模式切换、结果展开、词库导入、来源声明。
- 数据 `public/dict/cc-cedict.txt.gz`：CC-CEDICT 快照，约 12 万条，gzip 后 ~3.8 MB。
  **不进 Git**（与 WASM 内核同一策略，避免 clone 膨胀）：`pnpm dev` / `pnpm build` 前由
  `fetch-dict --if-missing` 自动拉取，快照存在且校验通过即跳过。
- 更新 `pnpm dict:fetch`，校验 `pnpm dict:check`（CI 可当门禁）。

### 为什么值得做

搜索引擎里带「新华字典」字样的在线站，绝大多数**未获授权**——商务印书馆已公开声明《新华字典》无网页版，
并指出这些站点音形义错漏常见（如「倔强 jiàng」标成 qiáng）。它们的商业模式是引流做范文下载、起名测字，
不在释义质量上下功夫。LocalForge 的解法不是做一个「更准的在线字典」，而是：

> **把词库变成用户手里的文件**——一次取回、永久离线、可替换、可审计、查询词不出浏览器。

这恰好是本项目一贯的价值观（文件不上传、离线可用、源码可读），而非又一个「在线工具」。

## 2. 三层解耦

```
数据层  CC-CEDICT / Kaikki JSONL / TSV      ← 可替换，parseDict() 按扩展名+内容嗅探
  │
索引层  buildIndex(entries)                  ← Map(词→条目) + 排序数组 + 拼音/首字母倒排
  │
检索层  search(index, q, { mode })           ← 精确 / 前缀 / 拼音 / 首字母 / 释义 / 模糊
```

换数据源不改检索代码，换检索策略不碰解析器。这是刻意的：词典数据格式有十几种，
而「怎么查」的交互是产品决策，两者耦合会让任何一方都难以演进。

## 3. 几个非直觉的实现点

### 3.1 拼音标调不是「加个音标」

CC-CEDICT 存的是数字声调（`ni3 hao3`），直接显示很丑。`toneMark()` 按《汉语拼音方案》标调：

| 规则 | 例 |
| --- | --- |
| 有 a 标 a | `da4` → `dà` |
| 有 e 标 e | `xie4` → `xiè` |
| `ou` 标 o | `shou3` → `shǒu` |
| `iu` 标 u | `liu2` → `liú` |
| `ui` 标 i | `gui4` → `guì` |
| 轻声（5）不标 | `ma5` → `ma` |

`ü` 在 CC-CEDICT 里写作 `u:`（`nu:3`），输入侧统一折叠为 `v`——没有中文输入法的人敲 `lv4 se4`
也能查到「绿色」。这是「可输入性」优先于「教科书拼写」的取舍。

### 3.2 前缀检索用二分，不做全表 startsWith

12 万条 × 每次输入都跑 `startsWith` 会让输入框卡顿。索引阶段把词条排序一次，
查询时二分定位，再线性收集同前缀项，命中上限即停。复杂度 O(log n + k)。

词表存成**「字符串数组 + `Int32Array`」的平行结构**而非 `{w, i}` 对象数组：
20 万条量级下省约 6–8 MB 常驻内存，排序与二分也更快（直接比字符串，不必读对象属性）。
同一份词表里**简体与繁体各写一条**，繁体词头（如「漢」）才能展开到「漢堡」——
否则繁体只能精确命中，前缀检索会整片漏掉。

### 3.3 模糊匹配设两道闸

- **长度闸**：`|len(a) - len(b)| > maxDist` 直接跳过，省掉绝大多数无望比较。
- **行内早停**：Levenshtein 逐行动态规划，某一行最小值已超过阈值就返回，不再算完整矩阵。

模糊**不作为 `auto` 模式的默认路径**——它要遍历候选集，必须由用户显式选择，
否则每次敲键都多几十毫秒，交互体感会碎掉。

### 3.4 解压走原生，fflate 只做兜底

`DecompressionStream('gzip')` 是浏览器原生能力，零依赖、不占包体。仅在老浏览器或异常时
`await import('fflate')` 动态加载兜底——这样 99% 的用户不会为兼容性多下载一个解压库。

### 3.5 IndexedDB 存什么、不存什么（v3 的最终裁决）

v1 的结论「索引不落库」过于一刀切，v2 又一度想给索引上缓存——两个都偏了。v3 想清楚的是：
**IndexedDB 该存的是「用户给的数据」，不是「我们自己算出来的数据」。**

- **不存索引**（52 MB 的倒排 + 平行数组）：
  - 写入本身就是一笔 structured-clone 的大开销（约数百 ms），加上读回时的二次克隆，
    每次访问省下的 500 ms 建索引时间，很大一部分又被读写吃回去；
  - 要面对 schema 版本、词库替换后的脏索引、配额清理——为一个查词工具背一套存储迁移不划算；
  - 词库文件本身已被 HTTP 缓存住，二次访问不重新下载；建索引又已搬进 Worker（见 3.7），
    就算 750 ms 也只发生在后台线程，不挡任何交互。
- **存自定义词库**（用户导入的原始文本，最大也就几 MB）：
  - 这是「用户给的数据」，丢了就要重新找文件，持久化是刚需而非优化；
  - `src/lib/dictstore.js`，与 `history.js` 同一策略：IDB 优先，不可用降级为会话内存态，
    不报错不阻塞；最多保留 5 份，超出淘汰最旧。
  - 刻意**不做 localStorage 兜底**：词库文本可达数 MB，localStorage 5MB 配额装不下，
    半途 `QuotaExceededError` 反而制造假故障。

### 3.7 建索引与检索都在 Worker，主线程零重活

`src/lib/dict.worker.js`（后台线程）+ `src/lib/dictclient.js`（主线程客户端）：

- **整个索引常驻 Worker 内存**，从不 postMessage 给主线程——省掉 50 MB 结构化克隆；
  主线程只收「条数 / 耗时」和「几十条检索结果」这类小消息。
- 协议就三个字段：`{ id, op, ... }` → `{ id, ok, payload | error }`，Promise map 管理；
- **降级路径**：Worker 构造失败（file:// 直开、老浏览器）或脚本加载失败时，
  动态 `import('./dict.js')` 在主线程跑同一套逻辑。`dictclient.js` 刻意不做静态
  import 内核——否则内核会被打进主包，Worker 化就白做了；
- 视图层用请求序号丢弃过期响应（防抖间隔内的旧查询不回写 UI）。
- **踩过的坑（v3）**：Vue 的 `ref()` 会把对象深层包成 reactive Proxy，而 Proxy 无法
  structured-clone，`worker.postMessage({ ipaTexts })` 直接抛 `DataCloneError`。
  传给 Worker 的一切必须先展开成纯对象。这个错误被客户端的降级逻辑**静默吞掉**，
  症状只是「悄悄变回主线程」——为此在降级路径上加了一条 `console.warn`，别删。

### 3.8 英语 IPA 音标：独立数据源，与主词库解耦

CC-CEDICT 是汉英词典，**天生没有音标**。给英文单词标音标没有用「更大的词典」解决，
而是接一份独立的开源音标库：[open-dict-data/ipa-dict](https://github.com/open-dict-data/ipa-dict)（MIT），
美式 125,927 词 + 英式 65,119 词，gzip 后共 ~1.3 MB，随 `scripts/fetch-dict.mjs` 与
主词库一起拉取、校验（`--only ipa-us` / `--only ipa-uk`）。

> 拉取注意：ipa-dict 的源文件是**纯文本**（.txt），CC-CEDICT 的源是 .gz。
> fetch 脚本按魔数（`1f 8b`）自动识别，纯文本源下载后**本地压缩成 gzip 再落盘**，
> 保证快照格式与 `*.txt.gz` 文件名一致——不然任何新克隆第一次 `pnpm dict:fetch` 就会撞上
> 「incorrect header check」。

- 只在查询**单个纯英文词**（`isSingleEnglishWord`，允许撇号/连字符、不含空格）时，
  Worker 顺带把读音附在检索结果上，主线程渲染音标卡（美 / 英两个标签 + 朗读按钮）；
- 朗读用 Web Speech API（系统本地语音，零外发请求、零依赖）；
- 两条音标流独立累积：美式与英式各自建 `Map`，同一词读音合并在一张卡里展示。

### 3.9 词库进 SW 预缓存清单（与其他内核同一待遇）

`public/sw.js` 的 `CORE_GROUPS` 新增 `dict` 组（三份 gz，约 5.5 MB）；
`src/lib/offline.js` 的 `CORE_GROUPS_META` 同步注册（首页离线面板出现卡片）；
`OFFLINE_NATIVE_TOOLS` 加入 `/dictionary`（零 WASM、纯本地即可用）。

词典页装载成功后自动发 `PRECACHE_CORES` 预缓存 `dict` 组——**访一次词典，
之后彻底断网也能查**，与 ffmpeg / tesseract 内核同一套机制，不另造轮子。


### 3.6 释义检索：倒排只负责召回，打分仍看原文

v1 查英文释义是**全表扫**：12 万条 × 每条 2–3 个释义 × 每次 lowercase + split，
实测 45 ms/次。`auto` 模式下英文输入无命中时也会落到这条路径，等于每次敲完一个词就付 45 ms。

v2 改为两段式：

1. **召回**：建 `byGlossWord` 倒排（词级），查 `bicycle` 直接从「含 bicycle 的文档」取候选，
   几十条而不是 12 万条；
2. **精细打分**：对候选**回到原始释义**重新定级（义项精确 45 / 义项前缀 38 / 子串 30）。

第 2 步是这个设计的关键。只做倒排、按「词是否出现」打分，会让 `bicycle` 的榜首变成
「軚」「中轴」这类释义里顺带提到 bicycle 的单字词——**速度上去了，排序废了**。
把打分逻辑留在原文上，排序质量与 v1 逐字一致，而候选只有几十条，耗时约 0.05 ms。

代价与取舍：

| 项 | v1（全表扫） | v2（倒排 + 精打分） |
| --- | --- | --- |
| 英文释义查询 | 45 ms | **0.1–0.3 ms** |
| 子串查询（`cycle`） | 45 ms | 45 ms（召回为空才兜底，极少走） |
| 建索引 | 382 ms | **750 ms** |
| 索引内存 | 42.6 MB | **52.4 MB** |

三个刻意的取舍：

- **只为纯英文释义建词级索引，义项级索引只给含中文的释义建**。CC-CEDICT 的释义全是英文，
  再建一遍「义项」索引会凭空多出 16 万个键、约 60 MB 内存，收益接近零；自定义中文词库才需要义项级。
- **长度 < 3 的词与 60 个英文功能词不进索引**（`the` / `to` / `a` …）。它们毫无区分度，
  却占据高频位置，去掉后唯一键直接少一大截。
- **子串兜底保留**。`cycle` 不是独立词，倒排召不回 `bicycle`；只在召回为空时才全表扫一次，
  冷僻查询不失效，常见查询也不为它付代价。

多词查询按 **AND** 处理：`green tea` 要求两个词都出现（词序无关），
整串连续命中额外抬到 40 分。

## 4. 体积与性能（实测，Node 22 / 桌面 Chrome）

| 阶段 | 数据（v1 → v2 → v3） |
| --- | --- |
| CC-CEDICT 原始文本 | ~6.9 MB |
| gzip 快照 | ~3.8 MB |
| 解析 | 70–95 ms |
| 建索引 | 382 ms → 750 ms → **Worker 内 680–900 ms**（不挡主线程） |
| IPA 音标库（美 / 英，MIT） | 3.2 + 1.7 MB 文本 → **0.85 + 0.42 MB gzip**，索引 ~4 MB 内存 |
| 精确 / 前缀查询 | < 5 ms |
| 英文释义查询 | 45 ms → **0.1–0.3 ms** |
| 子串兜底查询（`cycle`） | 45 ms（未变，仅召回为空时走） |
| 多词 AND 查询（`green tea`） | 45 ms → **< 1 ms** |
| 索引常驻内存 | 42.6 MB → **52.4 MB**（+IPA 词索引 ~4 MB） |

> 测量方式：`node --expose-gc`，同一份 125,423 条词库，建索引取 3 次重建后的稳定堆占用，
> 查询取 5 次最小值。浏览器端（Chrome / 桌面）建索引会再慢 10–20%，其余同级。

> 体积取舍：词库是**静态资源**，不进 JS bundle，不参与 `check:bundle`（该门禁只管 JS/WASM 内核）。
> 对 InfinityFree 的 10 MB 单文件上限、Cloudflare Pages 的 25 MB 上限均安全。

## 5. 边界：它不替代什么

| 需求 | 本工具 | 应当使用 |
| --- | --- | --- |
| 日常查字、汉英互译、拼音反查 | ✅ | —— |
| 断网 / 隐私敏感场景查词 | ✅ | —— |
| 《现代汉语词典》第 7 版的规范释义 | ❌ | 商务印书馆官方 App（98 元买断） |
| 词源、历史语义演变（学术级） | ❌ | OED（图书馆读者卡可免费登录） |
| 国家标准科技名词 | ❌ | 术语在线 termonline.cn（官方免费） |

CC-CEDICT 是**社区维护**的词典，覆盖广、更新快，但不是国家语委的规范文本。
把它当作「可审计、可离线、可替换」的工程方案，而不是权威辞书的替代品——这条边界写在 UI 里，
避免用户误用。

## 7. 后续可做（未实现，避免过度设计）

1. **部首 / 笔画检索**：CC-CEDICT 不含部首字段，需引入 Unihan 数据（`kRSUnicode`），是独立数据源。
2. **词频排序**：当前按命中权重 + 词长排序，缺乏真实词频；可接 SUBTLEX-CH 语料提升常用词优先级。
3. **StarDict / MDX 二进制解析**：`.ifo/.idx/.dict` 工作量大于收益（CC-CEDICT 已覆盖主场景）；
   MDX 生态更大但块结构与编码转换需要约一周。
4. **多词库并存**：导入的自定义词库已可持久化重载；改为「多源叠加 + 按源过滤」需要索引带 sourceId，留待真实需求出现。
5. **生词本**：直接复用 `dictstore.js` 的 IDB 通道（另开 store），配 Anki TSV 导出。
6. ~~建索引移入 Web Worker~~ → 已做（3.7）。~~索引落 IndexedDB~~ → 裁决为不缓存索引，改为持久化自定义词库（3.5）。
